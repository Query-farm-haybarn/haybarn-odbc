# CLAUDE.md — haybarn-odbc

Guidance for Claude Code working in this repository.

## What this repo is

**haybarn-odbc** is the ODBC driver for
[Haybarn](https://github.com/Query-farm-haybarn/haybarn) — an independent
derived distribution of DuckDB ("Haybarn, powered by DuckDB"), published by
Query Farm LLC. This repo is a **hard fork** of `duckdb/duckdb-odbc`, based on
upstream tag **`v1.5.5.0`** (duckdb-odbc's own 4-component
`vMAJOR.MINOR.PATCH.BUILD` scheme — the first three mirror the DuckDB engine
version, the 4th is an independent driver-only patch counter).

All Haybarn-specific changes are a small, curated **commit stack** on top of
the upstream tag — not scattered edits. Keep it that way: the stack must stay
easy to rebase onto future `duckdb-odbc` tags.

## Hard rules

- **Never rename the `duckdb::` C++ namespace, the C API, or any `duckdb_*`
  exported symbol** (see `duckdb_odbc.def` / `duckdb_odbc.map` / `duckdb_odbc.exp`
  — the `EXPORTS`/symbol lists must stay verbatim). Haybarn is intentionally
  ABI-compatible with DuckDB.
- **On-disk file names keep their upstream names** (`duckdb_odbc.rc.in`,
  `duckdb_odbc.def`, `include/duckdb_odbc.hpp`, etc.). Only build **target**
  names, artifact/library output names, and branding strings are rebranded.
  This keeps the diff against upstream minimal and the fork easy to rebase.
- **Trademark compliance is mandatory.** Product name is always "Haybarn",
  never "DuckDB Haybarn". DuckDB appears only descriptively. No DuckDB logo or
  duck-derived mark anywhere (see `winsetup/banner.bmp`, replaced with
  text-only Haybarn art). Keep the MIT `LICENSE` verbatim; keep `NOTICE`
  accurate. https://duckdb.org/trademark_guidelines.
- **When you change a user-facing driver string, update the tests that assert
  it.** `SQL_DBMS_NAME`/`SQL_DRIVER_NAME` ("Haybarn", 7 chars vs "DuckDB", 6
  chars) and the ODBC diagnostic vendor-identifier ("ODBC_Haybarn") both have
  length- and content-sensitive assertions in `test/tests/test_truncation.cpp`
  and `test/tests/test_session_init.cpp` — a driver-identity string change
  that isn't a same-length swap will break truncation-boundary tests silently
  if you don't recompute the expected lengths/offsets.
- **One commit = one concern.**

## Driver identity rename map

| Surface | Upstream | Haybarn |
|---|---|---|
| Registered driver name (`winsetup/setup.c`, `install.c`) | `DuckDB Driver` | `Haybarn Driver` |
| Default DSN (`winsetup/install.c`, `linux_setup/unixodbc_setup.sh`) | `DuckDB` | `Haybarn` |
| Shared library / CMake target (`CMakeLists.txt`, `CMakeLists.txt.in`) | `duckdb_odbc` | `haybarn_odbc` |
| Windows setup DLL target | `duckdb_odbc_setup` | `haybarn_odbc_setup` |
| `SQL_DBMS_NAME` / `SQL_DRIVER_NAME` (`src/odbc_api/info_api.cpp`) | `DuckDB` | `Haybarn` |
| ODBC diagnostic vendor-identifier (`src/odbc_driver/common/odbc_diagnostic.cpp`) | `ODBC_DuckDB` | `ODBC_Haybarn` |
| Windows registry keys | `ODBCINST.INI\DuckDB Driver`, `ODBC.INI\DuckDB` | `...\Haybarn Driver`, `...\Haybarn` |
| Windows `.rc` file metadata (`duckdb_odbc.rc.in`, `winsetup/setup.rc`) | CompanyName/FileDescription/ProductName = "DuckDB..." | "Query Farm LLC" / "Haybarn ODBC..." |

**Explicitly NOT renamed** (ABI-compat): `duckdb::` C++ namespace throughout
the vendored tree, `DUCKDB_VERSION` macro, all `duckdb_*` C-API exported
symbols, the standard `SQL*` ODBC entrypoint names, the `DUCKDB_ODBC_API`
build-visibility macro (internal, unused outside the CMake `DEFINE_SYMBOL`
property).

## The vendored DuckDB source = the trust root (most important invariant)

`src/duckdb/` is generated by `vendor.py` from a `--duckdb <path>` checkout
using that checkout's own `scripts/package_build.py`. **That path must point
at the Haybarn engine** (`~/Development/haybarn/haybarn`), not upstream
`duckdb/duckdb`. The assembled tree includes
`src/main/extension/extension_helper.cpp` (carries `HAYBARN_TRUST_ROOT`) and
`src/include/duckdb/main/extension_install_info.hpp` (carries the
`haybarn-extensions.query.farm` URLs) — so the vendored build embeds the
single Haybarn RSA key (core + community) and the Haybarn extension repo.
DuckDB-signed extensions will not load. **`CMakeLists.txt` is generated from
`CMakeLists.txt.in`** by `vendor.py` — any target-name/branding edit to
`CMakeLists.txt` must be mirrored in `CMakeLists.txt.in`, or it's silently
dropped on the next re-vendor.

### Regenerating the vendored source (after an engine bump)

**`OVERRIDE_GIT_DESCRIBE` is mandatory.** The engine reports its version via
`git describe`, and an rc commit sits *ahead* of the release tag, so a bare
describe yields a `-dev` version. DuckDB's
`ExtensionHelper::GetVersionDirectoryName()` then treats the build as a dev
build and resolves extensions under the **git source id** instead of the
version directory — which doesn't exist on `haybarn-extensions.query.farm`.
Stamp the release version instead:

```sh
cd ~/Development/haybarn/haybarn-odbc
SHA=$(git -C ~/Development/haybarn/haybarn rev-parse --short=10 HEAD)
OVERRIDE_GIT_DESCRIBE="v1.5.5-0-g${SHA}" python3 vendor.py --duckdb ~/Development/haybarn/haybarn
```

The `-0-` (zero commits since the tag) is what makes the version stamp clean
(`v1.5.5`, not `v1.5.6-devN`) while `DUCKDB_SOURCE_ID` still records the real
commit. Verify:

```sh
grep -E '#define DUCKDB_(VERSION|SOURCE_ID)' src/duckdb/src/function/table/version/pragma_version.cpp
grep -q HAYBARN_TRUST_ROOT src/duckdb/src/main/extension/extension_helper.cpp && echo "trust root OK"
grep -o 'haybarn-extensions\.query\.farm' src/duckdb/src/include/duckdb/main/extension_install_info.hpp
```

After re-vendoring, re-apply any target-name edits that live in
`CMakeLists.txt` (regenerated) vs `CMakeLists.txt.in` (hand-maintained
template) if they've drifted — diff the two before committing.

## Verifying it's actually Haybarn

```sh
brew install unixodbc   # macOS
make release             # -> build/release/libhaybarn_odbc.dylib
./linux_setup/unixodbc_setup.sh -u -D $(pwd)/build/release/libhaybarn_odbc.dylib
strings -a build/release/libhaybarn_odbc.dylib | grep haybarn-extensions.query.farm
```
Then over a connection (`DSN=Haybarn`): `SELECT version();` should report a
clean `v1.5.5`-shaped string (a `-dev` string means the re-vendor step above
was skipped), and `INSTALL httpfs; LOAD httpfs;` (not one of the 4
statically-bundled extensions) should succeed and resolve against
`haybarn-extensions.query.farm`.

## CI

- `.github/workflows/ODBC.yml` — build/test matrix (Linux amd64/arm64,
  Windows amd64/arm64, macOS universal). DuckDB-internal S3 staging Deploy
  steps and Azure Trusted Signing are removed (Haybarn defers Windows code
  signing, same as every other client fork).
- Release tags: `haybarn-v<MAJOR>.<MINOR>.<PATCH>.<BUILD>` (e.g.
  `haybarn-v1.5.5.0`), matching the org-wide `haybarn-v*` convention — unlike
  `haybarn-rust`/`haybarn-go`, nothing here forces a bare-tag scheme.
